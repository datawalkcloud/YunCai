## 0. 共同前提：先把三条口径定死

这三条现在代码里不统一或没有，两个模块都依赖它，必须在同一批改动里定下来。

| 口径 | 现状 | 定论 |
| --- | --- | --- |
| 账簿统计哪些凭证 | `TrialBalanceService.GetAsync` 遍历 `voucherRepository.GetAllAsync` **不过滤 Status**，草稿/已审核/已过账全部计入 | **只有 `VoucherStatus.Posted`（已过账）进入账簿与报表**。草稿与已审核凭证在页面顶部以「N 张未过账」提示，不参与金额 |
| 期间边界 | `AccountSet.ClosedPeriod`（yyyyMM）只用于禁止增删改凭证，账簿不看期间 | 账簿查询区间一律**按自然月对齐**（`StartDate` 归一到月初、`EndDate` 归一到月末），`ClosedPeriod` 之后的期间允许查询但标注「未结账」 |
| 余额方向 | `Account.Direction` + 净额正负硬塞借/贷（`SplitBySign`） | 保留现有「净额按正负拆借贷」的显示口径（科目余额表/报表已如此），**但账簿内部一律用 `netDebit = 借 - 贷` 计算**，只在输出层做 `SplitBySign` |

> 第 1 条是**行为变更**，会改变现有科目余额表/资产负债表/利润表的数字（未过账凭证被剔除）。落地时要同步 `AGENTS.md`，并在过账链路上加提示：结账前必须把凭证全部过账（`VoucherService` 已有「已过账不能删除/已结期间锁定」，缺「存在未过账凭证」的拦截提示）。

## A2. 校验规则（唯一容易出错的地方）

集中在新建 `src/YunCai/Application/Accounts/AccountAssistGuard.cs`，由 `VoucherService.CreateAsync/UpdateAsync` 在现有末级科目校验处调用（`Application/Vouchers/VoucherService.cs:117`、`:185`、`:207`）：

1. 分录上出现的 `AssistType` 必须 ∈ 该科目 `AccountAssistType`，否则报「科目「1122 应收账款」未设置「部门」辅助核算」。
2. 科目设置的 `IsRequired=true` 的类型，分录必须至少挂 1 个该类型档案。
3. `AssistItem.Type` 必须与挂载的 `AssistType` 一致；`IsLeaf=false` 的档案不可记账（对齐科目的末级约束）；`IsEnabled=false` 的档案不可用于新凭证。
4. 档案所属账套必须与凭证账套一致（跨账套越权是 Guid 型外键最容易出的 bug）。
5. 现金流类型（`AssistType.CashFlow`）是**唯一允许在非现金科目分录上出现**的类型吗？—— 不。定论：现金流维度**只挂在现金/银行存款/其他货币资金类分录上**，其他科目挂现金流报错。这条决定了现金流量表能否自动取数，务必写进单测。
6. 反审核/删除凭证时级联清理 `voucher_entry_assists`（EF 侧 `DeleteBehavior.Cascade`，与 `voucher_entries` 一致）。
7. 已结期间（`AccountSet.IsDateClosed`）或已过账凭证不可改辅助核算 —— 沿用 `EnsureDraft()` 即可，但 `Voucher.UpdateEntry` 目前不带 assists，需在 `UpdateEntry` 签名里一并传入并整体重建。

# 模块 B：账簿查询（一张地基 + 七个投影）

## B1. 核心判断

柠檬云 9 张账页共用同一个「查询条件」面板（12 个开关）+ 同一套取数口径。我们的正确做法**不是写 9 个 Service**，而是：

```
LedgerDataSetFactory  →  LedgerDataSet（一次读入，请求内复用）
        ↓                       ↓
   Facts（扁平事实）      Balances（两级聚合）
        ↓                       ↓
   序时账 / 明细账        科目余额表 / 总账 / 凭证汇总表 / 核算项目余额表·明细账·组合表 / 多栏账
```

新增目录 `src/YunCai/Application/Ledgers/`。

## B2. 事实模型与聚合键

```csharp
// LedgerFact.cs —— 一条凭证分录 = 一行事实（凭证头信息已展平，全账页共用）
public sealed record LedgerFact(
    Guid VoucherId,
    DateOnly Date,
    int Period,                  // yyyyMM，预计算，避免每处 Date.Year*100+Month
    string Word,
    int Number,
    string VoucherNo,            // "记-1"
    VoucherStatus Status,
    int LineNumber,
    string Summary,
    Guid AccountId,
    decimal Debit,
    decimal Credit,
    string Preparer,
    string? Reviewer,
    int AttachmentCount,
    IReadOnlyList<LedgerAssistRef> Assists);   // (AssistType, AssistItemId)

public readonly record struct LedgerAssistRef(AssistType Type, Guid AssistItemId);

/// <summary>聚合主键：科目，或「科目 × 单个档案」。同一分录挂多个同类型档案时按档案各计一次。</summary>
public readonly record struct BalanceKey(Guid AccountId, AssistType? AssistType, Guid? AssistItemId);
```

`BalanceKey` 是整套账簿的心脏：**科目余额表用 `(AccountId, null, null)`，核算项目三表用 `(AccountId, type, itemId)`**。两级聚合共用同一个累加器，因此「核算项目余额表合计 = 科目余额表对应科目」这条恒等式天然成立，可以写成单测。

```csharp
// LedgerDataSet.cs
public sealed class LedgerDataSet
{
    public required DateOnly StartDate { get; init; }
    public required DateOnly EndDate { get; init; }
    public required IReadOnlyDictionary<Guid, Account> AccountsById { get; init; }

    public required IReadOnlyList<LedgerFact> Facts { get; init; }        // 区间内、已过账
    public required IReadOnlyDictionary<BalanceKey, decimal> OpeningNet { get; init; } // 起始日之前的累计净额（借-贷）
    public required int UnpostedVoucherCount { get; init; }

    public IReadOnlyList<LedgerFact> Filter(LedgerQueryOptions o);
    /// <summary>两级聚合：科目级 + 科目×档案级。</summary>
    public LedgerBalances Aggregate(LedgerQueryOptions o);
}

public sealed class LedgerBalances
{
    public IReadOnlyDictionary<Guid, AccountBalance> ByAccount { get; init; }

public readonly record struct AccountBalance(decimal OpeningNet, decimal PeriodDebit, decimal PeriodCredit)

```

## B3. `LedgerDataSetFactory`：一次性装载

现有 `TrialBalanceService` 每次 `GetAllAsync(accountSetId)` 全表读实体再内存累加（`Application/Reports/TrialBalanceService.cs:44-78`）。账簿有 7 张表，不能各读各的。

设计成**每个 HTTP 请求装载一次**：`AddScoped<LedgerDataSetFactory>`，工厂内部 `Lazy<LedgerDataSet>`（同请求内多个 Service 共用）。装载实现改为 **投影查询**，不再物化 `Voucher` 聚合根：

```csharp
var facts = await db.Vouchers.AsNoTracking()
    .Where(v => v.AccountSetId == accountSetId
             && v.Date >= start && v.Date <= end
             && v.Status == VoucherStatus.Posted)          // 口径 0.1
    .SelectMany(v => v.Entries, (v, e) => new { v, e })
    .Select(x => new FactDto(x.v.Date, x.v.Word, x.v.Number, x.v.Status, x.v.Preparer,
                             x.v.Reviewer, x.v.AttachmentCount,
                             x.e.LineNumber, x.e.Summary, x.e.AccountId, x.e.Debit, x.e.Credit,
                             x.e.Id))
    .ToListAsync(ct);
// assists 单独一次查询按 entryId 分组，再拼进 Facts（避免 EF 翻译不友好的嵌套集合）
```

期初与跨年累计同理，用一条 `GroupBy(AccountId)` 的 SQL 拿到 `start` 之前的净额，不在 C# 里遍历全历史（这是现有实现最主要的性能风险点）。`OpeningBalance` 走 `accounts.opening_balance`（口径与现在一致：启用期初 + 起始日前分录净额）。

**性能决策与阈值**（明确写死，避免无谓争论）：

- 阶段一（本设计）：全量内存聚合，单账套 ≤ 5 万张凭证 / ≤ 30 万条分录可接受（投影查询 + 单表 group by）。
- 触发阶段二的条件：任一账页 P95 > 1.5s，或单账套分录 > 30 万条。
- 阶段二做法：新增物化表 `account_period_balances(account_set_id, period, account_id, assist_type, assist_item_id, debit, credit)`，在**过账/反过账/删除凭证的事务内增量写入**，账页改为读期间汇总 + 当期明细。
- **现在不做阶段二**，但 `BalanceKey` 与 `AccountBalance` 的形状就是那张表的主键与列 —— 迁移时零重构。别在阶段一就往仓储里塞缓存（缓存的正确性代价远高于收益）。

## B4. 查询条件模型：`LedgerQueryOptions`

对齐柠檬云那张隐藏 modal 的 12 项，**一个 record 全部账页共用**，缺项时取默认值：

```csharp
public sealed record LedgerQueryOptions
{
    public required DateOnly StartDate { get; init; }   // 归一到月初
    public required DateOnly EndDate { get; init; }     // 归一到月末
    public string? AccountFrom { get; init; }           // 编码或区间串，如 "1001,1122,1501-1503"
    public string? AccountTo { get; init; }
    public int? MaxLevel { get; init; }                 // 科目级别
    public CurrencyScope Currency { get; init; } = CurrencyScope.Base;  // Base=综合本位币 All=所有币别 Rmb=人民币
    public string? SummaryKeyword { get; init; }
    public LedgerSortBy SortBy { get; init; } = LedgerSortBy.VoucherNumber;  // VoucherNumber | VoucherDate
    public bool ShowAssist { get; init; }
    public bool ShowOnlyLeaf { get; init; } = true;     // 只显示最明细
    public bool ShowCounterAccount { get; init; }       // 显示对方科目
    public bool HideZeroBalance { get; init; }          // 余额 0 不显示
    public bool HideNoActivity { get; init; }           // 无发生额且余额 0 不显示
    public bool ShowQtyAmount { get; init; }            // 数量金额式 —— 依赖数量核算，一期恒 false
    public AssistType? AssistType { get; init; }        // 核算项目类账页用
    public AssistType? SecondaryAssistType { get; init; } // 组合表：主 × 次两维
    public Guid? SingleAccountId { get; init; }          // 多栏账：单科目
}
```

`Currency` 与 `ShowQtyAmount` 一期只保留枚举与字段（值恒 `Base` / `false`），**但不实现多币种与数量核算**，等 P0 后面的「外币核算」「数量核算」批次再填。这不是过度设计，而是避免那时把 7 张账页的 options 全改一遍。

科目区间表达式解析器（可单测的小工具，别内联到 LINQ）：

```csharp
// AccountCodeSelector.cs
/// <summary>把 "5001,5051,5601-5603" 解析成前缀集合；区间按 4 位数字段做闭区间。</summary>
public static bool Matches(Account account, string? expression)
```

匹配语义必须是**前缀匹配**（`code == p || code.StartsWith(p)`），因为选了 `1122` 就要带出 `112201`；这依赖 `accounts.code` 是父编码为前缀的既有不变量（`Account.AddChild` 已强制，见 `Account.cs:113`）。区间端点按编码长度相等才做数值比较，长度不同视为非法并回退为「逗号拆分的独立前缀」，避免 `1501-1503` 误吞 `150101`。

## B5. 七张账页 = 七个投影 Service

全部落在 `Application/Ledgers/`，统一签名 `GetAsync(Guid accountSetId, LedgerQueryOptions options, CancellationToken)`，内部只依赖注入的 `LedgerDataSetFactory`。**每个 Service 只做投影与格式化，不碰仓储。**

| Service | 账页 | 投影逻辑要点 |
| --- | --- | --- |
| `TrialBalanceService`（改造现有） | 科目余额表 | 改为消费 `LedgerBalances.ByAccount`；`HideNoActivity` 时才列示；行按 code 排序；上级行由下级汇总（现有实现只列出现过的科目，需补「非末级行 = 子级合计」） |
| `SubsidiaryLedgerService` | 明细账 | 按科目分段：段头=期初（方向+净额）→ 逐笔（日期/凭证字号/摘要/借/贷/方向/余额）→ 段尾「本月合计」「本年累计」。`ShowCounterAccount` 时补对方科目列 = 同一凭证内**另一方向**的科目串（借方行取贷方科目，反之） |
| `GeneralLedgerService` | 总账 | 按期间（月）一行：期初/借/贷/期末/方向；直接取 `ByAccount` 按月分组累加 |
| `VoucherJournalService` | 序时账 | 纯 `Facts` 排序输出（日期/凭证号/摘要/科目编码/科目名称/借/贷/**制单人/审核人/附件数**），按 `SortBy` |
| `VoucherSummaryService` | 凭证汇总表 | 科目 × 借/贷合计 + 表头【凭证数 N 张 / 附件数 N 张】，张数按 `VoucherId` distinct、附件数按凭证取一次不重复累加 |
| `AssistLedgerService` | 核算项目明细账 / 余额表 / 组合表 | 余额表：行=档案，列=科目（`ShowAssist` 时的 pivot 展开）；明细账：同 `SubsidiaryLedgerService` 但 `BalanceKey` 换成 `(Account,type,item)`；组合表：`AssistType × SecondaryAssistType` 双维交叉 + 「主类别小计」行 |
| `MultiColumnLedgerService` | 多栏账 | 单科目（默认取 `options.SingleAccountId`，如 5602 管理费用）→ 其**直接下级科目作栏**，逐笔行 × 栏次金额 + 月末合计 |
| `AgeingAnalysisService` | 账龄分析表 | 固定 7 档 `≤30/30-60/60-90/90-180/180-360/360-1080/>1080`；账龄起算日=分录日期，截止日=`EndDate`；未核销余额算法见下 |

### B5.1 明细账余额连续性（最容易写出 bug 的地方）

逐笔余额必须满足：`running = openingNet + Σ(debit - credit)`（按该 key 的时间序），且**最后一行余额 == 科目余额表期末余额**。实现要求：

- 排序必须稳定：`Date → Word → Number → LineNumber`，`SortBy=VoucherDate` 时改为 `Date → Word → Number`（同一凭证内仍按行号）。
- 期初行不参与发生额；「本月合计」「本年累计」只统计非期初行。
- 红字冲回走负数分录（`Voucher.GuardEntry` 已允许负数单边，`Voucher.cs:284`），明细账直接显示负数，**不做正负转换**。

### B5.2 账龄一期口径（先可用，别追求自动核销）

柠檬云有「账龄设置」暗示可自定义核销。一期明确**不做手工核销**，采用余额推龄：

1. 取该科目（默认池 1122/1123/1221/2201/2202/2203/2241，可由 `AccountFrom` 覆盖）× 档案的期末净额。
2. 该 key 的分录按时间**倒序**消耗期末净额：先冲最晚的分录，剩余净额落在哪笔就归入那笔的账龄档。
3. 输出：档案行 × 7 档金额 + 比例 + 合计。
4. 页脚标注「按先进后出法估算账龄，未做单据核销」。二期做核销表 `settlements(source_entry_id, offset_entry_id, amount)` 时替换该算法，DTO 不变。

验收（含单测断言）：

1. **恒等式一**：任一条件下，`科目余额表` 合计借 = 贷（页脚试算平衡文案为绿）。
2. **恒等式二**：明细账最后一行余额 == 科目余额表该科目期末（对 20 个随机科目做属性测试）。
3. **恒等式三**：核算项目余额表按科目合计 == 科目余额表该科目（前提是辅助核算必录）。
4. **恒等式四**：序时账借方合计 == 科目余额表本期借方合计 == 凭证汇总表借方合计。
5. 总账按月展开，各月借贷合计 == 科目余额表区间合计。
6. 未过账凭证不出现在任何账簿金额中；页头显示「N 张未过账」。
7. `AccountFrom="1122,1501-1503"` 命中 1122 及其全部下级、1501/1502/1503 及下级，且不吞 `150101` 之外的错配。
8. `HideNoActivity=true` 时余额 0 且无发生额的科目不列示；`=false` 时列示。
9. 5 万张凭证下，明细账（单科目区间）< 800ms，科目余额表 < 1.2s（本地 PostgreSQL，实测记录进 PR）。
10. 现有科目余额表页面行为不回退（除口径 0.1 的过账过滤，需在 PR 描述里显式声明）。

## D. 已知取舍与后续衔接

- **不做**：多币种（`CurrencyScope` 留字段不实现）、数量金额式（`ShowQtyAmount` 同上）、手工核销、打印服务端模板。这些各自是 P0 里独立批次（外币核算、数量核算），塞进本次会把 12 人日变 25 人日。
- **衔接期末结转**：结转凭证需要「按损益科目批量取本期发生额生成一张凭证」，直接复用 `LedgerBalances.ByAccount` 的 `PeriodDebit/PeriodCredit` —— 这就是为什么聚合器不能只算期末余额。
- **衔接现金流量表**：`AssistType.CashFlow` 挂在现金类分录上的约束（A2 第 5 条）是现金流量表自动取数的唯一前提，务必在单测里锁死。
- **领域陷阱提醒**（AGENTS.md）：本项目实际用旧准则编码体系（如 3001 实收资本）。账簿里凡按编码首位/前四位判类别的地方一律改用 `Account.Category` 字段，**不要**新写按首位推断的逻辑；`InferCategoryAndBalanceSheetService` 的兼容问题属于报表模块，不在本设计范围内。
